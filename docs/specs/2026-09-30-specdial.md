# Design: specdial

Is a coding agent becoming a compiler? A compiler turns one source into one
behaviour, every time. An agent given the same request twice can return two
programs that behave differently. This experiment measures how many
behaviourally distinct programs an agent produces for the same request, and
how that number falls as the request gets more precise.

The post's claim takes the shape: "at spec level X, agents converge to one
behaviour on these functions and not on those; what still diverges is what a
human still has to read or specify", with numbers.

## Question and measurement

For each (function, spec level, agent) cell, run N fresh sessions. Each run
leaves one implementation of a fixed exported function. Every implementation
is executed on the same held-out input corpus and its outputs recorded.

- **Behaviour signature**: the vector of canonicalised outputs over the
  corpus. A thrown error records as the token `THROW`; the message is ignored,
  since two messages for the same rejection are not a behavioural difference
  a caller branches on. A run that exceeds the per-input time limit records
  `TIMEOUT` for that input.
- **Distinct behaviours (k of N)**: number of distinct signatures in the cell.
  A compiler scores 1. This is the headline.
- **Effective behaviours**: `exp(Shannon entropy)` over signature frequencies,
  so one stray run out of fifteen does not read the same as fifteen-way
  disagreement.
- **Modal share**: fraction of runs producing the most common signature.
- **Agreement with the reference**: fraction of runs whose signature equals
  the reference implementation's, plus per-run fraction of inputs agreeing.
  Reported as "agreement with the author's intent", not correctness: at the
  lowest level many behaviours are defensible readings of the request.
- **Distinct source texts**: number of distinct implementations after
  normalisation (esbuild transform, comments and whitespace stripped). Tests
  the expectation that code text stays diverse while behaviour converges,
  which is the point about what line-by-line reading is actually reading.
- **Where divergence survives**: every corpus input carries a hand-assigned
  category (for example `quoted-value`, `crlf`, `duplicate-key`). For each
  cell, the categories on which runs still disagree. At the top level this is
  the list of decisions no spec pinned down.
- **Cross-agent convergence**: the same counts with all agents' runs pooled
  per (function, level). Do Claude and Codex converge to the same behaviour,
  or to different ones?

## Spec levels

A monotone ladder: each level is the previous one plus one artifact. The
exported name, file path and TypeScript signature are given at every level,
because the harness has to call the function; everything else varies.

| Level | The agent is given |
|---|---|
| L0 ticket | a one-to-three sentence request, written the way a teammate would file it, plus the signature |
| L1 + examples | L0 plus a visible vitest file of 5 to 8 example-based tests |
| L2 + prose spec | L1 plus the precise plain-English spec (the mutgap `spec.md`) |
| L3 + properties | L2 plus visible fast-check property tests stating the invariants |

The reference implementation passes every visible test at every level;
`check_tasks.py` enforces this. The L0 ticket is written before looking at
which decisions the corpus probes, and committed before the first run, so the
ticket is not tuned to be vague.

Ordering examples before the prose spec is a choice: example tests are what a
team typically has before anyone writes a precise spec. The design does not
measure prose-only (L2 without L1); see Out of scope.

## Functions

Five pure functions from the mutgap corpus, reused because each already has a
real-world reference implementation, a precise spec and hand-written oracle
tests, and because it links the two posts. All come from repositories under
`github.com/iceinvein`.

| Function | Decisions a request leaves open |
|---|---|
| `parseEnv` | comments, `export ` prefix, first vs last `=`, quote stripping, duplicates, blank values |
| `toCsv` | header source, missing keys, quoting rules, escaping, trailing newline |
| `globToRegex` | `*` vs `**`, `**/` at root, metacharacter escaping, anchoring, braces |
| `safeFilename` | forbidden chars, whitespace, dot handling, empty fallback, extension dot |
| `formatDuration` | unit thresholds, rounding, null input, `1m 60s` edge |

For `globToRegex` the output is a `RegExp`, so its behaviour signature is the
match result of the returned regex over a fixed path list per pattern, not the
regex source.

Stateful and clock-dependent functions (`parseResetAt`) are left out: the
corpus would need operation sequences and a pinned clock, which adds harness
risk without changing the question.

## Input corpus

Per function, held out from the agent at every level:

- 40 to 80 hand-written inputs, each tagged with a category, covering every
  decision in the table above and every clause of the prose spec;
- 500 generated inputs from fast-check with a fixed seed, biased towards the
  function's special characters, tagged `generated`.

The visible L3 property tests use different generators and no fixed inputs
from the corpus. `check_tasks.py` fails if any corpus input appears literally
in a visible file.

## Agents and repeats

- Claude Sonnet 5.5 and Claude Opus 5.5 via `claude -p`, with
  `--setting-sources project` (the mutgap isolation, verified there).
- Codex via `codex exec` with a scratch `CODEX_HOME` holding only `auth.json`
  and a `config.toml` pinning model and effort, as in interview-signal. A
  probe run verifies isolation before any real run.
- N = 15 per cell. The CLIs expose no temperature setting; each tool's
  default sampling is what a user gets, and is what is measured.

| Functions | Levels | Agents | Repeats | Runs |
|---|---|---|---|---|
| 5 | 4 | 3 | 15 | 900 |

Estimated Claude usage, API-priced: mutgap averaged $0.19 per run for writing
tests; writing one small function should be similar or cheaper, so about
$115 for the 600 Claude runs, plus Codex on the operator's plan. The pilot
(one function, all four levels, 3 repeats per agent, 36 runs) comes first
and replaces this estimate with a measured one.

## How a run works

As interview-signal: each run is a fresh Docker container from a pinned
image (both CLIs at the host's versions, vitest, fast-check and tsx
preinstalled), running as a non-root user, with only the run's work dir
mounted and a network that reaches the model APIs and nothing on the host or
LAN. Claude runs with `--setting-sources project`, web tools disallowed and no
MCP; Codex with a scratch `CODEX_HOME` that turns off web search and app
connectors. `probe.sh` checks the isolation before any paid run.

The work dir holds `package.json`, `src/<name>.ts` as a stub with the
signature that throws, and the level's visible files. The prompt is one
sentence asking for the implementation, pointing at whatever files the level
provides, plus the test command when tests are visible. The agent never sees
the reference, the corpus or other runs. The implementation it leaves behind
is copied into `runs/<fn>__<level>__<agent>__r<rep>/impl.ts`.

A run whose implementation does not load (syntax error, missing export) is
kept and counted as its own behaviour class `NOLOAD`, and reported
separately.

## Scoring

- `score.py` loads each `impl.ts` in a Node child process via `tsx`, calls the
  function on every corpus input with a 1-second per-input limit, and writes
  `signature.json` (outputs) and `score.json` (hash, agreement, load status).
- `analyze.py` prints every number the post quotes and emits the chart data.
- Canonicalisation: JSON with sorted object keys; `undefined` recorded
  distinctly from `null`; `-0` distinctly from `0`; non-finite numbers as
  strings.

## Pre-registered expectations

Written down before the pilot so the post can say which held.

1. Distinct behaviours fall monotonically from L0 to L3 in most cells.
2. Not every cell reaches 1 at L3.
3. Distinct source texts stay close to N at every level.
4. At L0, agents agree with the reference on under half of runs.
5. Pooled across agents, L3 converges less than within one agent.

## Repository layout

`../specdial/`, MIT, public, mirroring mutgap:

- `tasks/<fn>/`: `reference.ts`, `stub.ts`, `ticket.md`, `examples.test.ts`,
  `spec.md`, `properties.test.ts`, `corpus.json` (inputs and categories),
  `meta.json` (source commit)
- `run.sh`, `score.py`, `analyze.py`, `check_tasks.py`
- raw transcripts gitignored; `impl.ts`, `result.json`, `score.json`,
  `signature.json` committed

## Out of scope

- Prose-only (L2 without examples) and properties-only arms. They would
  answer "English or tests?", a second question for a second post.
- Multi-file or stateful tasks. Small pure functions give the cleanest
  behaviour signature; the limitation is stated in the post.
- Reviewer experiments (line-by-line vs contract-first review). Separate
  study.

## Risks

- **Corpus coverage**: two implementations can differ on an input the corpus
  lacks, so k is a lower bound. Mitigated by category coverage of every spec
  clause plus generated inputs; stated as a lower bound.
- **Contamination**: the source repos are public. An agent reproducing the
  reference from memory would inflate convergence; the L0 agreement rate
  shows whether that happens.
- **Ticket authorship bias**: the ticket sets how much L0 diverges. Frozen
  and published before the first run.
- **Codex isolation**: probe before any run.

## Decisions at sign-off (2026-09-30)

1. Reuse the five mutgap functions.
2. Sonnet 5.5, Opus 5.5 and Codex, N = 15, 900 runs.
3. New public repo `specdial` beside mutgap, MIT.
4. Runs use interview-signal's container isolation, not mutgap's temp dir:
   the source repositories are public, so a run that can reach GitHub (a
   Codex app connector did in interview-signal) could fetch the reference.
   Agent-written code is also scored inside the container with no network.
